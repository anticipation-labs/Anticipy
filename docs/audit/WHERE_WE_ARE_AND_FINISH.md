# Where We Are, And The Finish Line

_Definitive honest status — synthesized from the five pillar audits and three research tracks (onboarding-UX, voice-loop, vision/definition-of-done). For Omar. Dated 2026-06-17._

---

## Bottom line

No, it is not all done — but the engine is far more real than a demo, and the gap is now specific and nameable rather than diffuse. The deep machinery works: three input doors converge on one source-agnostic brain, memory is durable and self-healing, and the cardinal-sin and money guards are layered in code. The live-action evidence is thinner than it sounds and must be stated honestly: one calendar create-and-read-back fired live once (the durable glassbox proof has since rotated out and is not re-confirmable on disk today, and was not re-run this session), and one outbound SMS was reported delivered (the SID lives only in markdown — RECEIPTS/HANDOFF — with no independent read-back; treat as UNCONFIRMED, especially because the project's own history corrected an EARLIER live-SID claim as a fabrication). The ONE thing blocking certification is the throttled model brain — the OpenRouter "moat" that decides task-vs-vent runs at 15–53s/call instead of ~3s, which means the single most important capability (the inference itself) has never been measured at runtime, and the 10,000-run certification harness is capacity-blocked at ~12% dropped obligations. The human-experience gap is just as real and separate: there is no front door, no in-app onboarding screen, no in-app account/phone connect, and no real-URL deployment — a stranger literally cannot self-onboard from a screen today, because the polished web app jumps straight into a localhost dev console. So we have a strong brain that is starved and unmeasured, behind a product that has no doorway — fund/unthrottle the model and build the onboarding shell, and most of the rest is wiring we already have.

## Do they work together?

The end-to-end spine is genuinely wired as one path, and the seam evidence is strong on the deterministic skeleton and weak exactly where it must be live.

- **Input → one brain:** Real. Typed `POST /owner/ingest`, MP3 `POST /owner/ingest-file` (real local Whisper+ffmpeg), and always-on mic `POST /listen/start` all end at the byte-identical `core.owner_ingest` call (main.py:722/774/792), verified by text scan + AST walk. Inbound non-YES/NO SMS also routes into the same door (inbound.py:118). This is the strongest integration in the system: the brain is provably source-agnostic.
- **Brain → memory/intent:** Real and fixed-order. `_owner_ingest_inner` runs observe → moat (`_expand_tasks_with_model`) → intent-resolve → consolidate-dedup → memory capture, BEFORE the card-build loop (control_core.py:1117-1129 precede 1131+). Critically this means PREVIEW == REALITY: memory and intent fire identically whether the route previews or executes. One capture chokepoint (`live_memory.capturer.capture`) with double-capture guarded.
- **Brain → autonomy:** Honest but oversold. The spine (`on_event`) is the only act/ask/silent authority, monotonic toward safety. But `classify_autonomy` is post-hoc OBSERVABILITY only — it labels the finished card and enforces nothing; grep confirms no UI/API/executor branches on the mode. The "6 modes constrain autonomy" framing fails the enforced-not-prompted bar.
- **Action arm:** Real wiring. API arm registered last on the bus so the real worker wins; `INTENT_MAP` is the single execution source of truth; no-API intents reroute API → browser with no orchestrator change. Browser actions are always confirm-first (YES required from app or SMS, single resolve door).
- **Proof/read-back:** Real for API (second independent execute wrapped in `confirm_stable_artifact`, orchestrator rejects self-attested proof). WEAKEST SEAM here: the browser centerpiece path never writes result back onto the card (only flips to "running"); the found result lives only in SMS + (rotating) glassbox.
- **Text-back:** Real and unified — one `TextChannel` carries reminders, asks, and browser-result texts through one mock/live decision and one audit trail.
- **Follow-up:** BROKEN at the end. `plan_follow_up` is computed but nothing ever fires it (no code converts `when_ts` into a nudge; no UI render site). The "I'll check back and nudge" promise is currently silent.

**Strongest integration:** the three input doors → one source-agnostic brain → memory/intent → dedup, all in a fixed PREVIEW==REALITY order. **Weakest seam:** the tail — browser result never lands on the card, and follow-up is computed but never delivered, so the "remembers and comes back to you" loop does not close in code today.

## The user journey to the goal

Walking the literal target — stranger finds it → opens it → onboards → connects accounts+phone → talks/it calls back → it works with them → a beautiful agent that does what it meant to.

1. **Finds it (a real front door / URL).** NOT YET. There is no real-URL deployment (off-localhost is owner-gated; cloudflared installed, unused). No pre-signup trust-first landing. Research bar is ~60s-to-value loginless trial; we have nothing public.
2. **Downloads / opens.** PARTIAL → NOT YET for a stranger. The native macapp is not distributable (hard-coded `REPO=/Users/omarebrahim/Anticipy`), signed but NOT notarized, and `@main` renders only a browser-launcher card — the premium onboarding/connect/main SwiftUI is DEAD CODE. The Chrome extension is dev-mode "Load unpacked" only, not Web-Store published. The web app opens but lands in a localhost dev console with banned artifacts and pre-filled SAMPLE data.
3. **Onboards clearly (<=60s, <=3 screens).** NOT YET. There is no onboarding UI at all — name/people/preferences/scan are raw API POSTs. The engine-side onboarding logic (discover, clarify, "Nothing was invented" thin-data honesty) is real and tested, but a non-technical user has nothing to click. This is the highest-leverage buildable gap.
4. **Connects accounts + phone.** NOT YET in-app. `/connect` is a readiness CHECKLIST whose buttons are external deep-links to vendor consoles ("this page connects NOTHING"). The engine HAS a managed-OAuth authorize path (`authorize_connection_loop` → `POST /connections/authorize`) but the UI never calls it. No phone OTP/consent flow exists; the Twilio row deep-links to the console. The elaborate vendor-name scrubber is itself a symptom of the manual hand-off.
5. **Talks to it / it talks + calls back.** PARTIAL (text) / NOT YET (voice). Inbound free speech and YES/NO resolution are wired and the leg-by-leg pieces are proven, but the full human round-trip (Omar actually texting the number → auto-reply) was never run. The signature 2:45 VOICE call has NEVER been placed live; two-way ConversationRelay needs a public wss URL not proven stood up — today's realistic voice path is speak-one-line-and-hang-up. No SMS→voice escalation, no delivery-state feedback loop, no STOP/quiet-hours compliance layer.
6. **Works WITH them (acts for real, remembers, comes back).** PARTIAL. Calendar create+read-back fired live once (proof since rotated out of glassbox, not re-confirmable on disk today). Browser cart-add is UNCONFIRMED — its sole evidence is commit b82e660's own message; it was not reproduced, and the path is currently code-broken (chromium-1161 absent), so it is not a proven datapoint. The model intelligence is OFF in every test (provider-gated), the live memory-enrichment organs are all stubs, and follow-up never fires. So it acts in one narrow proven case (calendar, once, stale) and does not yet demonstrably remember-and-return.
7. **A beautiful agent that does what it genuinely meant to.** NOT YET as a shipped experience. The premium design system, copy-scrubber, and safety philosophy are real assets, but the premium shell + scrape-you onboarding is unbuilt, the inference quality is unmeasured, and the headline trust mechanic (preview-before-acting, money-is-the-only-stop) is never surfaced at the connect moment where it would earn the grant.

## The finish line

Ordered, highest-leverage first. Two tracks: what I can build now, and what only Omar can unblock.

### (A) Buildable autonomously now

1. **Build the real in-app onboarding + connect flow (the front door).** A dedicated `/welcome` (or `/onboarding`) route: trust-first first screen ("Before I start listening — who am I helping?"), one input, then wire the existing `POST /connections/authorize` managed-OAuth path THROUGH the UI so Connect launches the provider's own consent screen and lands back already-connected (redirect/popup) — replacing the dead-end vendor-console deep-links. Make `/connect` rows perform the connect in-app and fill progress as a result. This is the single highest-leverage move and removes most of the vendor-name scrubber's reason to exist.
2. **Kill demo scaffolding in the live UI.** Blank the pre-filled SAMPLE transcript and DEFAULT_MEMORY people; "start over" should blank, not restore fake data. A real new user must never inherit Omar's sample world.
3. **Make the "Get to know me" recap the 60-second reward.** Sequence the `onboard_scan` read-only recap ("here's your day, here's the 3 tasks I already inferred — I invented nothing") to fire immediately after an in-app connect, not buried at the bottom of a checklist.
4. **Add in-app phone-number capture + OTP + non-prechecked SMS consent UI** (Twilio Verify pattern), so the 2:45 loop's number setup is an end-user step, not an operator console task. (Live delivery still owner-gated — see B.)
5. **Wire follow-up so it actually fires — and do not ship the nuisance-nudge bug.** This is bigger than "convert `when_ts` through TriggerWatcher": there is NO existing trigger read site for `follow_up` at all (TriggerWatcher fires only on loop-ledger `remind_ts`/`due_ts`/`created_ts`; `follow_up` appears nowhere in trigger.py or engine.py), AND the one UI label (app/page.js:332) keys on a card-action literal `'follow_up'`, NOT the attached plan dict — a key mismatch. So scope it as: build a `follow_up` read/fire site, fix the app/page.js:332 key mismatch, de-dupe the per-ingest fresh-timestamp churn, AND tighten `_AWAIT` matching so it does not over-trigger. Today `_AWAIT` matches bare verbs (order, return, reply, confirm) in `source_text`, so a do/ask card that merely MENTIONS such a verb would get a spurious follow-up; wiring follow-up as-is would fire nuisance nudges. Add key/disposition exclusions (not disposition alone) before turning it on. Close the "I'll come back to you" loop in code.
6. **Land browser result on the durable card.** Make the centerpiece `research_or_find_item` path call `_persist_card`, and have `_resolve_browser_card_record` write the found result/screenshot/URL back onto the card (parity with the goal path's `goal.proof`). Add a minimal in-flight job record so a restart mid-run doesn't lose the AFTER text.
7. **Add the missing safety/regression unit tests** for `classify_autonomy`, `plan_follow_up`, and the pure harm/triage predicates into the project suite, so the deterministically-correct floors can't silently regress. Add two specific drift/auto-act surfaces this list previously missed: (a) a regression test pinning `press_go.py`'s harm-CATEGORY interpretation to the spine's `detrimental` flag — press_go is a THIRD independent consumer of `harm.assess` that keys off harm category rather than the broad detrimental flag, and its lockstep with the spine was grepped, not traced, so it can drift; and (b) unit tests guarding `resume_waiting`/`_drive`, so the low-risk `_confirm_task_goal` paused goal cannot auto-execute if a future caller is ever added (today it is safe only because its sole caller is a test script — brain_loop_part2.py).
8. **Add the compliance layer** (cheap, no creds needed to author): STOP/UNSUBSCRIBE/QUIT keyword honoring in the inbound poller, and an 8am–9pm-local quiet-hours guard before any proactive send. Schedule `deliver_digest` once daily at a sane local hour.
9. **Wire the implied-tier moat structurally** (the centerpiece capability, currently NOT-MET): add a who-said-it-to-whom / addressee axis to triage, an implied-tier commitment-confidence number + published threshold, and un-stub `ProactiveEngine.tick` so the "surface it later, cold" loop exists. (Quality of this still depends on B1.)
10. **Fix the code-broken browser path and the false-ready/stale-README signals.** The centerpiece browser path is presently CODE-BROKEN on this machine, not merely emitting a false-ready signal: the chromium-1161 cache is ABSENT, and the runner fails at "chrome binary missing" (runner_use_runner.py:215-222), while `available()` (browser_use_link.py:72-85) checks only bridge python + runner existence and never the chrome binary — so it returns ok=True against a binary that cannot launch. Fix: have ARM B's `available()` actually probe for the chrome binary and report not-ok when chromium-1161 is missing (and restore/install the cache so the path can run). Also correct the extension/macapp READMEs that invert reality.
11. **Include the short resolve code in the browser-ask outbound SMS.** The browser ask's outbound SMS does NOT carry the short code, so a bare "YES" from the phone only resolves when it is the ONLY pending ask; with multiple pending asks a bare YES resolves NOTHING (a clarification is sent instead). On the centerpiece SMS path this silently fails to resolve under concurrent asks. Put the short code in the outbound text so a bare-YES reply resolves the right ask deterministically.
12. **Wire a DeleteEvent intent — or restate the round trip honestly.** There is NO DeleteEvent intent anywhere in the engine (greps empty), so the "create → read-back → delete" claim is really create+read-back and test-artifact cleanup is MANUAL — a recurring STRAY-EVENT source flagged in FAILURE_MODES. Either wire a real DeleteEvent intent so the round trip closes and artifacts clean themselves, or restate the round trip everywhere as "create + read-back; cleanup manual." The prose already corrects the claim; this adds the remediation to the plan.
13. **Give the per-person BROWSER route a credential mechanism.** TokenVault is wired to ApiHand but NO code path wires per-user tokens into BrowserHand — so a user whose app has no API and must go through the browser has no credential mechanism at all. This is separate from the "token vault EMPTY" API-arm gap; the browser-route vault is wholly unwired. Build per-user credential injection for BrowserHand before the multi-user browser story can work.

## Honest risks & unknowns

- **The product IS the inference, and the inference is the one thing not measured.** Vent-as-task false-positive rate and implied-task catch-rate are unmeasured at runtime because the moat was throttled. Everything safety-related that depends on the model being ON (the `force_ask` vent downgrade, the live decider, the mega-eval) is currently un-reverified or inert under the stub provider.
- **Receipts carry an honesty scar.** The project already corrected one FABRICATED live voice/SMS SID claim. The current outbound-SMS and browser-round-trip "proven-live" claims rest on the same kind of evidence (SIDs/commit messages in markdown, no independent read-back). Treat both as UNCONFIRMED until a fresh failable check passes. Do not put them in investor framing as proven-live.
- **Three marketing/summary claims are explicitly REFUTED by the audit** and must not leak: typed input does NOT call one brain with no card-building (it's a multi-stage pipeline, model is one optional stage); memory is NOT written for every observed line (vents/prefs dropped first); intent does NOT run for every route. The "create → read-back → delete" round trip is really create+read-back; delete is by hand (a known stray-event source).
- **Durability holes on the real paths.** The browser centerpiece path skips `_persist_card`, so a declined web task vanishes from the durable board (the F-011 anti-stranding fix doesn't cover the common case). Fire-and-forget browser runs lose state on restart. The one credible calendar live proof rotated out of glassbox and isn't re-confirmable from the current checkout.
- **Latent over-action surfaces (harmless only because nothing reads them today).** The dead `_AUTO_ACTIONS` allow-list (grepped — referenced only at its definition site) means a `{disposition:'do', action:'make_purchase'}` card is labeled AUTO_DO right now; if any future code ever trusts `autonomy_mode` as act-authorization it inherits a real over-action hole. `_confirm_task_goal` builds a paused goal whose driver (`resume_waiting` → `_drive`) has no production caller — but the step it builds is Risk.low (create_event/write_memory), so it BYPASSES the orchestrator approval gate; it is safe TODAY only because its sole caller is a test script (brain_loop_part2.py). If any future endpoint or background loop ever calls `resume_waiting`, the paused confirm-task goal auto-executes with NO human YES. The defensive fix is to guard `resume_waiting` itself (A7b), not merely to avoid wiring it. Separately, `press_go.py` is a THIRD independent consumer of `harm.assess` that keys off harm CATEGORY rather than the broad `detrimental` flag; its lockstep with the spine was grepped, not fully traced, so it is a real safety-drift surface over time (A7a).
- **Pattern-bound safety guards.** Money/checkout regexes (`PURCHASE_GUARD`/`CHECKOUT_URL_RE`) and the navwall sensitive-host list are curated/heuristic — non-English locale, icon-only pay buttons, odd checkout URLs could evade; `ANTICIPY_NAVWALL_ALLOW_PRIVATE=1` (a CI relax) would re-open SSRF if ever set in prod. The browser-use arm's money stop on a logged-in session is prompt-only, which is exactly why act-over-CDP is hard-refused — that refusal is the load-bearing line.
- **Scale and isolation unknowns.** The token vault is EMPTY, so all live API uses the shared Arcade key — no per-user blast-radius isolation yet. Worse on the browser arm: TokenVault is wired to ApiHand but NO code path wires per-user tokens into BrowserHand, so the per-person BROWSER route (a user whose app has no API and must go through the browser) has no credential mechanism at all (A13). Vector retrieval is a full linear scan (fine single-user, won't scale). The whole connect/onboard surface is owner-gated single-user, not the multi-user front door investor-readiness requires.
- **The running engine's actual live/mock mode was NOT inspected this session.** No `.env*` file was found by the searches run here, and the running process's actual mode was not inspected to avoid triggering live behavior; `factory/.halt` is present. So the claim that the running process is safely in mock rests on CERTIFICATION_NOW.md's assertion plus `factory/.halt` — it is ASSERTED, not verified by an inspected process env. A certification doc claiming "started SAFE" should be backed by an inspected env, which this audit did not do; treat the running process's mode as unverified until a fresh env check passes.
- **Compliance is a hard external dependency, not a code task.** A2P 10DLC (texts won't deliver without it) and Google CASA Tier 2 (Gmail/Calendar capped at 100 users until done) are time-boxed, paid gates that must be on the roadmap now.
