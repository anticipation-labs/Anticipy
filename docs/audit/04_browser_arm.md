## routing+autonomy
BROWSER ROUTING + AUTONOMY in engine/anticipy_engine/core/control_core.py.

OVERVIEW: An owner transcript line travels: _owner_ingest_inner (1117) -> _expand_tasks_with_model MOAT split/vent-judge (1120) -> _intent_resolve (1121) -> _consolidate_obligations (1122) -> per-line: on the execute path _spine_card (1142), on the preview path the regex card (1144). After a card exists there is a dedicated BROWSER GATE (1158-1170). Autonomy mode is attached LAST, post-hoc, by classify_autonomy over the finished card dict (1247-1250). On YES, resolve() (2068) fires the browser agent.

TWO WAYS A WEB TASK BECOMES A CARD:

1. CONFIRM-FIRST browser ask (_browser_action_ask, 738). The card is disposition=ask, route=browser, action=browser_action, id="br_"+sha256(...)[:18] (749 — deterministic so re-ingest is idempotent, F-011). It registers a pending ask in self.proactive.pending[ask_id] with category=browser_action and browser_task/browser_url (752-755), persists it (755), and IMMEDIATELY TEXTS the owner the plain-English ask (761). It does NOT run the browser; it waits for YES.

2. AUTO-PREPARE a cart (resolved_cart). In _spine_card (866-877): when the regex shaped action == find_or_cart_without_purchase (owner_mode.py 470-472, fired by _BROWSER+_NO_BUY i.e. an explicit "don't buy"/research request), the spine asks memory read_context (873) whether the exact item+store is resolvable. If _has_external_context (572) is FALSE (no confident item/store), it falls back to _browser_action_ask (875) = the confirm-first ask. If TRUE, it sets shaped.args["resolved_cart"]=True (877) and FALLS THROUGH to execute via the action spine (882 self.feed) — the cart is auto-prepared in a throwaway browser (browse_task, via orchestrator alternates at 388 and the runner's money/checkout guard), carrying a memory_resolution receipt. This is Omar's "prepare when confident" law.

THE BROWSER GATE (1158-1170) — when does the confirm-first ask fire vs not: it fires ONLY when execute_actions AND card.route=="browser" AND disposition NOT in (blocked, remember) AND action != "browser_action" (already an ask) AND NOT args.resolved_cart AND NOT line.force_ask (1159-1163). I.e. an UNRESOLVED web do/research card is rewritten to _browser_action_ask (1168) and appended (1169). A RESOLVED cart (resolved_cart set in the spine) SKIPS this gate and stays an auto-prepared do-card. A money line is disposition=blocked (owner_mode 446/474-476/501) so it never reaches the gate. A vent-adjacent line (force_ask) is excluded so a vent never spawns a browser ask.

AUTO-PREPARE vs ASK DECISION (the crux): The branch point is memory confidence inside _spine_card. find_or_cart_without_purchase + resolvable item/store (read_context + _has_external_context True) -> AUTO-PREPARE cart (877, falls through to execute). find_or_cart_without_purchase + NOT resolvable -> _browser_action_ask (875). research_or_find_item / any other route=browser do-card that is not resolved -> caught by the gate at 1158 -> _browser_action_ask (1168). So: AUTO-PREPARE requires (a) an explicit no-buy/research shape AND (b) memory resolving the exact item+store; otherwise ASK first.

HOW AUTONOMY_MODE ATTACHES: It is NOT chosen during routing — it is read off the finished card by classify_autonomy (proactive/autonomy.py 24) at control_core 1247-1250, then logged into out["middle_trace"]["autonomy"] with chosen/rejected modes (1253-1260). Mapping (autonomy.py 30-45): disposition=remember->REMEMBER_ONLY; disposition=blocked (money)->PREPARE_THEN_STOP; action=draft_or_confirm_message->PREPARE_THEN_STOP; action=="browser_action"->AUTO_DO_WITH_OPT_OUT (37, "visible web task, reversible, no buy"); disposition=do OR execution.decision=act->AUTO_DO (covers the resolved_cart auto-prepared cart); disposition=ask->CLARIFY_FIRST. So a confirm-first browser ask card = AUTO_DO_WITH_OPT_OUT (verified deterministically), and an auto-prepared resolved cart = AUTO_DO (verified). Money browser card = PREPARE_THEN_STOP (verified).

YES -> EXECUTION (resolve, 2068): resolve() checks self.proactive.pending[ask_id] for category=="browser_action" BEFORE the normal goal funnel (2075-2076). It pops+persists the pending (2077-2078), writes the resolution onto the durable card via _resolve_browser_card_record (2081), then on YES kicks asyncio.create_task(_run_browser_and_confirm(...)) (2083-2085) so the 1-3 min run never blocks the reply, returning state="running". _run_browser_and_confirm (773) texts "On it..." (780), runs browse_act on the real site via asyncio.to_thread (784, hands/browser_use_link), then texts the result or a failure message (790-796). The same YES path is reachable from an SMS "YES" (the pending ask is the single resolvable object).

DECLINED WEB TASK DURABILITY (_resolve_browser_card_record, 2030): on NO, the durable owner card record at data_dir/owner_cards/{ask_id}.json gets state="declined", resolution={ask_id,approved:False}, owner_card.status="declined" written back (2040-2046), and _sync_owner_loop_status(ask_id,"declined") (2049-2050). Because card.id == ask_id == the record filename, this is a direct lookup. owner_cards() derives the board status from record state+resolution, so a declined web task shows "declined" on the board instead of a stranded "open" (F-011). resolve() returns {approved:False, declined_action, goal_id} (2090-2091).

_confirm_task_goal (685): a SEPARATE path, NOT browser — it builds a PAUSED resolvable Goal for a model-caught non-web task (a call / vague to-do) so the app YES actually executes (create_event for a calendar hold, else a write_memory open_loop). Used by the moat-task rescue branch (937), giving disposition=ask, route=voice_text, action=confirm_owner_task. It never auto-drives the goal (no cardinal-sin auto-act); only /resolve drives it.

_web_start_url (719): maps plain language to a start site (amazon/opentable/doordash/walmart/target/etc.) else Google (verified: 'amazon' -> amazon.com, unknown -> google.com). Always the throwaway browser, never the owner's logged-in Chrome (docstring 722-723).

## hands+runner
There are TWO independent browser arms in the engine, plus a per-user token vault. They do NOT share a driver.

ARM A — Extension/CDP arm (the user's OWN Chrome). Entry: `engine/anticipy_engine/hands/browser_hand.py` `BrowserHand` (Worker, handles ["browse_task","read_page","prepare_form"], browser_hand.py:136-139). It does NOT drive Chrome itself; it delegates over a transport `BrowserLink`. `BrowserLink` (`engine/anticipy_engine/core/browser_link.py:34`) is an authenticated WebSocket to a Manifest-V3 Chrome extension (`extension/manifest.json`, permissions include "debugger" + host "<all_urls>"). The extension runs INSIDE the user's real Chrome and executes observe/act in the live tab. There is also a CDP fallback transport `NativeBridgeLink` (`engine/anticipy_engine/core/native_bridge_link.py:221`) that, when the extension socket is down, talks Chrome DevTools Protocol on localhost:9222 — and `_ensure_cdp_chrome` (native_bridge_link.py:817-857) will subprocess-launch the user's `/Applications/Google Chrome.app` with `--remote-debugging-port=9222 --user-data-dir=<their profile> --profile-directory=Default`, i.e. their REAL logged-in Chrome. ControlCore wires `BrowserHand(self.browser_link, gateway=agent_gateway, fallback_link=native_bridge, ...)` (control_core.py:357-370); `_active_link()` (browser_hand.py:141-146) picks the extension link if connected else the native bridge.

Inside ARM A, the planner is `WebVoyagerAgent` (`engine/anticipy_engine/agent/webvoyager.py:1388`), used only for `browse_task` when a gateway is present (browser_hand.py:162-163). It is a task-state controller: PLAN (model writes 3-6 subgoals), then a loop (run(), webvoyager.py:2118-2275) of observe -> build set-of-marks prompt -> model picks a JSON action {click|type|scroll|navigate|answer} -> `_act` -> `_observe_ready`. observe/act are sent through `self.link.send_browse(new_id(), "observe"|"act", args)` (webvoyager.py:1398, 1434) — the SAME WS/CDP transport. `read_page`/`prepare_form` (and `browse_task` with no gateway) go through `_handle_once` -> `link.send_browse(job.id, intent, args)` (browser_hand.py:266) directly to the extension.

ARM B — browser-use arm (a THROWAWAY browser, separate process). Entry: `engine/anticipy_engine/hands/browser_use_link.py` `browse_read`/`browse_act` (lines 145-298). This is a 3.10-safe client that NEVER imports browser_use; it shells out (`subprocess.run`, browser_use_link.py:229) to `browser_use_runner.py` executed by a separate Python 3.11 venv `engine/.bu-venv/bin/python` (browser_use_link.py:46). The runner (`browser_use_runner.py:175-338`) is the ONLY place `browser_use` (v0.13.1, MIT) is imported; it builds a `browser_use.Agent` with OUR OpenRouter model (ANTICIPY_MODEL_SMART, default google/gemini-2.5-flash) and, by default, a throwaway Chromium under a temp `user_data_dir` (browser_use_runner.py:251-279) — a cached chromium-1161 binary, NOT the user's Chrome. It communicates by one JSON line on stdin and one sentinel-tagged JSON line on stdout (`__ANTICIPY_BU_RESULT__`, parsed by `_parse_runner_output`, browser_use_link.py:130-142). ControlCore uses this arm for the live "web task -> texted ask -> YES -> result text" round trip via `_run_browser_and_confirm` -> `browse_act` (control_core.py:773-799).

Intents (ARM A): browse_task (general agent or single observe), read_page (read-only single navigate+observe), prepare_form (safe WRITE: `FormPrepareAgent` fills a form to the submit screen then STOPS — never submits, always returns needs_human with filled-field + screenshot proof, browser_hand.py:166-212). Modes: MODE_MOCK (control_core default via ANTICIPY_HANDS_MODE) runs the same deterministic gates then returns a loudly-labeled mock artifact (browser_hand.py:214-237); MODE_LIVE delegates to the real transport.

REAL vs mock: ARM A LIVE and ARM B drive REAL sites (the extension in real Chrome; browser-use in a real throwaway Chromium). ARM A MOCK is a no-browser stub. There is NO HTTP "gateway/mock site" being driven — the only mock is the in-process MODE_MOCK artifact. Caveat: ARM B's `available()` returns ok=True here (bu-venv symlink + runner exist), but the cached chromium-1161 binary is ABSENT on this machine, so a throwaway run would fail at runner's "chrome binary missing" guard (browser_use_runner.py:215-222) unless a loopback CDP attach is used.

token_vault.py is NOT a browser driver. It is the per-user encrypted token mesh: TokenVault (encrypt-then-MAC at rest, scrypt KDF, one file/user), TokenBroker (hands a redacting SecretToken the LLM can't reach), ConnectorRegistry (routes (user,app) to "api"|"browser"|"voice_text"). The "browser" route is just a routing label that says this user's app has no API and must go through the browser hand; the vault itself never opens Chrome. It currently backs ApiHand (control_core.py:349-351), not BrowserHand.

## safety-guards
The browser arm has TWO independent executors, and safety is enforced in CODE at the bottom of both — not merely in the model prompt. The cardinal guarantee everywhere: money/checkout/login are HARD STOPS, and a web page's own text can NEVER authorize an action.

EXECUTOR A — the user's own Chrome via the WebVoyager planner (engine/anticipy_engine/agent/webvoyager.py), driven over a transport (BrowserLink WS extension or NativeBridgeLink CDP).
  Money (deterministic, runs INSIDE agent.run() BEFORE any act is dispatched to the browser):
   - PURCHASE_GUARD regex (webvoyager.py:68-82) matches only UNAMBIGUOUS final-pay control labels ("place your order", "buy now", "complete purchase/order/checkout/payment", "pay now", "pay $<amount>", "confirm order/purchase/pay", "place bid", "subscribe and pay"). Bare "submit"/"checkout" are deliberately EXCLUDED so cart/nav controls aren't false-stopped.
   - The action-guard in the loop (webvoyager.py:2224-2241): for any click/type/navigate/submit, if the current URL OR a navigate target matches CHECKOUT_URL_RE (webvoyager.py:88-97, e.g. /checkout, /placeorder, amazon gp/buy, ?payment=) it returns _done(...stopped_for_safety=True) and "STOPPED at a checkout/payment page — did NOT place the order". For a click, if the targeted element's label matches PURCHASE_GUARD it returns stopped_for_safety. Crucially this is BEFORE self._act() (webvoyager.py:1430-1436) sends anything to Chrome, so the money click never reaches the browser. webvoyager.py:324-326 in browser_hand maps stopped_for_safety -> needs_human (hand back to owner).
  Login: LOGIN_URL_RE (webvoyager.py:101) drives _commerce_wall_kind -> "login" hand-off (webvoyager.py:1264-1271).

## roundtrip
The "working together" round-trip (web task -> texted plain-English ask -> owner YES -> browser agent runs -> result texted back) is implemented across control_core.py, inbound.py, and text.py. Two distinct ask round-trips exist; the browser one is Omar's centerpiece.

OUTBOUND ASK (the offer). In ControlCore.owner_ingest's per-line loop, a card whose route=="browser" and disposition not in (blocked,remember) and not already action=="browser_action" is converted to a texted ask by _browser_action_ask (control_core.py:660-771, gated at 1002-1014). That method: (a) maps the plain task to a start site via _web_start_url (control_core.py:639-657; known sites like amazon/opentable, else google; never the user's logged-in Chrome); (b) mints ask_id=new_id() and registers it DIRECTLY into proactive.pending[ask_id] = {goal_id, action, reason, category:"browser_action", browser_task, browser_url} then _persist_pending() (control_core.py:692-699); (c) sends the owner a jargon-free SMS NOW via self.text_channel.send (control_core.py:702-708): "Hey — I heard you want to {task}. Want me to take a look and report back? Just reply YES or NO."; (d) returns an OwnerTaskCard with card.id==ask_id, disposition="ask", route="browser", action="browser_action", execution={ask_id, goal_id, goal_state:"waiting"} (control_core.py:709-715). _persist_owner_card writes this card to data_dir/owner_cards/{card.id==ask_id}.json with state="waiting" (control_core.py:1353,1406-1417).

YES HANDLING (the resume — the ask_id/goal resume path). Both the app YES button and an SMS YES funnel through the SINGLE door ControlCore.resolve(ask_id, approved) (control_core.py:2068). Before the normal goal funnel, resolve checks proactive.pending.get(ask_id): if category=="browser_action" (control_core.py:2075-2091) it pops+persists the pending, calls _resolve_browser_card_record(ask_id, approved) to flip the durable card record (running on YES, declined on NO), and on YES does asyncio.create_task(self._run_browser_and_confirm(browser_task, browser_url, ask_id)) — fire-and-forget so the reply never blocks (1-3 min run) — returning {approved:True, browser_action:True, state:"running", goal_id:ask_id}. On NO it returns {approved:False, declined_action} and never runs the agent. Non-browser asks fall through to proactive.resolve_ask (control_core.py:2092) which resumes the EXACT paused goal (the classic Room-4 path).

SMS YES path. _inbound_scheduler polls Twilio every ANTICIPY_INBOUND_POLL_SECONDS (main.py:94-115). InboundPoller.poll_once (inbound.py:88) gates strictly on OWNER_PHONE (refuses if unset) and _norm_phone(from)==owner. A body matching _REPLY=^\s*(yes|no)\b(?:[sep]([A-Za-z0-9]{4,32}))?...$ (inbound.py:50) goes to _resolve_reply (inbound.py:127): a >=4-char code prefix-matches a pending ask_id, or a bare YES/NO resolves only when EXACTLY ONE ask is pending; ambiguous (0 or >1) resolves NOTHING and sends one bounded clarification SMS. The match resolves via self.core.resolve(ask_id, approved) (inbound.py:143) — the same F18 single door — so a YES texted from the phone hits the identical browser_action branch as the app button. Seen-sids persist atomically and are marked BEFORE acting (never replays an approval).

RESULT DELIVERY (the confirmation leg / voice_text channel). _run_browser_and_confirm (control_core.py:773-800): logs browser_action_start, sends the BEFORE text via text_channel.send ("On it — I'm looking into \"{task}\" on the web now. I'll text you what I find."), runs the agent in a thread res = await asyncio.to_thread(browse_act, task, url=url, max_steps=16), then sends the AFTER text "Done — {answer[:500]}" on success or an honest "I tried to {task} but couldn't finish it..." fallback, and logs browser_action_done. The send channel is TextChannel (text.py:33-40): live Twilio REST when ANTICIPY_CHANNELS_MODE=live + creds, else mock that records to .sent. (notify_user at control_core.py:1834 is the parallel send seam used by the classic ask path and inbound clarifications, routing through ChannelWorker send_text.)

PROOF / READ-BACK ON THE CARD. browse_act (browser_use_link.py:145-160) -> browse_read with act=True runs the open-source browser-use agent in a throwaway (non-logged-in) browser and returns a BrowseReadResult with success + result, honest-by-construction (any blocker yields success=False with an error, never faked).
