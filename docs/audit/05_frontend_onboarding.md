## onboarding
**What the user experiences:** There is NO user-facing onboarding screen in this repo. The engine serves no HTML/form/wizard (grep for StaticFiles/HTMLResponse/templates in engine/anticipy_engine/main.py returns nothing). The only thing a human visually sees is the Chrome extension popup (extension/popup.html + popup.js), a 240px dark panel reading "Anticipy" with a single status dot/line that says one of: "checking engine...", "connected to engine", or "engine offline". It has NO buttons — no "Connect Google", no "Sign in", no form fields. So onboarding is a developer/API-driven flow today, not a self-serve product screen.

The actual setup happens through HTTP/WebSocket calls, not clicks the user makes:
- CONNECT CHROME: the user installs the unpacked extension (extension/manifest.json). Its MV3 service worker (extension/background.js) auto-connects to the local engine over an authenticated WebSocket at ws://127.0.0.1:8787/ws/extension (fetches a token from /ws/token first, line 35-44). Once the socket is up the popup flips to "connected to engine". That is the entire "connect your Chrome" act — install + the worker dials in. No login inside Anticipy.
- CONNECT GOOGLE/ACCOUNTS (two ways). (a) Chrome scrape: someone POSTs /onboard/scan; the engine tells the already-connected extension to run doDiscoverConnections (background.js:142), which opens Gmail/Calendar/Drive/Outlook/Slack/Notion (the DEFAULT_DISCOVER_SERVICES list, background.js:14-21) in a tab group inside the user's OWN logged-in Chrome and reads ONLY a logged-in-vs-signin DOM signal (an account/avatar/sign-out control minus a sign-in wall) — never contents, never credentials — then POSTs {service,logged_in,url} back to /onboard/discover. (b) API scan: POST /onboard/scan_api probes Arcade managed-OAuth (client.tools.authorize on GoogleCalendar.ListEvents, Gmail.ListEmails, Slack, Notion; control_core.py:1481-1499) plus any locally-vaulted tokens, and for confirmed-connected accounts actually READS them to derive honest profile facts.
- CONNECT AN ACCOUNT THAT NEEDS AUTH: each not-yet-connected service becomes a "Connect X for Owner Action Engine" open-loop card. The user (or app) calls POST /connections/authorize {id}; for an api-route service in live mode the engine returns a real Arcade connect_url the user opens and approves (control_core.py:1979-1984). For a browser-route niche service it just checks the browser link is up.
- CONNECT PHONE: there is NO phone OAuth/verification in onboarding. body.phone is just a typed string stored as an identity memory (owner_onboarding.py:84-86); Twilio voice/SMS is configured server-side via env (TWILIO_*, ALERT_PHONE), and the clarifying phone call is explicitly LIVE-DEFERRED (clarify.py:11, summary.delivery="live-deferred (Twilio voice)").

**Flow:**
- Install the unpacked Chrome extension (extension/manifest.json). Its background.js service worker fetches a token from GET /ws/token and opens an authenticated WebSocket to ws://127.0.0.1:8787/ws/extension; engine calls browser_link.attach (main.py:1480-1487). Extension popup now shows 'connected to engine'.

- Engine ingests the scan: core.onboard_discover -> scan_to_onboarding (connection_scan.py:38) maps each logged-in service to an OwnerConnectionIn — route 'api' for known services (gmail/calendar/outlook/slack/notion/drive) else 'browser' for niche apps; status 'connected' if the token vault already holds it, else 'needs_auth'. It then runs the SAME owner_onboard path, so a discovered service becomes a profile card + a 'Connect X' open-loop (control_core.py:1719-1754).
- AUTO account discovery (server-side, no extension): POST /onboard/scan_api -> probes Arcade managed-OAuth authorize for Calendar/Gmail/Slack/Notion + locally-vaulted tokens; confirmed-connected accounts feed onboard_discover (source 'api_scan'), then _read_onboarding_profile READS the live calendar/Gmail and derives honest facts (e.g. 'You have N events in the next two weeks', busiest weekday, frequent contact >=2 shared events, recent email volume, frequent correspondent >=2 threads) written to the profile drawer (control_core.py:1471-1717). If reads are thin it writes nothing and returns 'No facts assembled. Nothing was invented.'
- CONNECT a needs_auth service: POST /connections/authorize {id of the open-loop} -> authorize_connection_loop (control_core.py:1922). api route + live mode: returns a real Arcade connect_url + 'open the connect URL and approve access', or 'already connected'. browser route: confirms the browser helper is linked. Read-only — it never executes an action.
- Once a connection flips to 'connected' (via re-onboard with that status), _close_connected_setup_loops marks the matching 'Connect X' open-loop done (control_core.py:1810-1832), retiring the setup task.
- PROFILE-BUILD a person/entity (separate enrichment): POST /onboarding/profile {name, sources:[public URLs]} -> SSRF-gated (_assert_public_source_url, main.py:908) -> ProfileBuilder reads each public page READ-ONLY via the browser arm: one COARSE whole-page overview (medium trust) + FINE per-field pulls for role/org/location (low trust, needs_cross_check). Every fact carries value+source_url+confidence+trust; unread pages become blockers, no fact invented (profile_builder.py).
- CLARIFYING CALL plan: GET/POST /onboarding/clarify -> builds the same profile then clarify_payload runs the deterministic planner: ranked 'couple of questions' — source disagreements first (read back conflicting values), then low-confidence confirmations, then unreadable-source blockers, then missing-core-field gaps, capped at ~5 (clarify.py:257-312). The Twilio voice delivery itself is live-deferred.
