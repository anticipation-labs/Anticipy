**Architecture:** Undo is a **compensating plan in the same lineage**, never a

def test_undo_never_touches_the_finished_plan():
    """cancel() raising on completed work is a load-bearing scar
    (workflow.py: 'cancel never retracts completed work'). A cancellation that
    erased the record of a real-world effect would be worse than no undo."""
    done = _succeeded_plan(goal="book Santouka Thursday 7pm")
    fresh = undo(done, reference="MB-8941",
                 cancel_url="https://santouka.test/cancel/MB-8941",
                 owner_words="tapped undo on book Santouka Thursday 7pm")
    assert done.state is PlanState.SUCCEEDED, "the original must stay terminal"
    assert fresh.plan_id != done.plan_id
    assert fresh.lineage_key == done.lineage_key, "one errand, one lineage"
    assert fresh.facts["undo_of"] == done.effect_key
    assert fresh.consequence is Consequence.CONSEQUENTIAL

def test_the_undo_goal_is_built_from_the_plan_never_re_triaged():
    """Sending 'undo' back through a model would let meaning decide WHICH
    booking dies. That is how you cancel the wrong one."""

    fresh = undo(done, reference="MB-8941", cancel_url="u", owner_words="w")
    assert "Santouka" in fresh.goal and "MB-8941" in fresh.goal

def test_a_second_undo_of_the_same_booking_is_the_same_plan():

```python
def undo(plan: "Plan", *, reference: str, cancel_url: str,
         owner_words: str) -> "Plan":
    """Undo is a NEW plan, never a state change on the finished one.

    cancel() raises on completed work and must keep raising: a cancellation
    that retracted a SUCCEEDED plan would erase the record of something that
    really happened in the world. So the finished plan stays exactly as it is
    and a compensating plan is minted beside it, in the same lineage, so the
    feed and _open_card_in_lineage still see ONE errand.

    The goal is built arithmetically from what the original plan RECORDED.
    It is never re-triaged: handing the word "undo" back to a model would let
    meaning decide which booking dies.
    """
    goal = f"cancel {plan.goal} — reference {reference}"
    fresh = new_plan(
        goal=goal,
        consequence=Consequence.CONSEQUENTIAL,
        lineage_key=plan.lineage_key,
        facts={"undo_of": plan.effect_key,
               "reference": reference,
               "cancel_url": cancel_url},
        authority_text=owner_words,
    )
    return approve(fresh, owner_words=owner_words)
```

## STAGE 2 — the auto-run lane — **STRUCK, NOT SCHEDULED**

**Both adversarial judges killed Stage 2 as designed, and they were right.**
Recorded here rather than quietly dropped, because the reasoning is the useful
part and the next person will otherwise re-propose it.

### The central claim was false

The design's whole safety argument was: *"the release is the executor's
possession of a captured undo handle, which is a fact, not a judgement."*

It is not a fact. **Every field of that handle is page-authored input.**
`policy` is a sentence the site printed. `cancelUrl` is an href the site
rendered. `deadline` is a date the site typed. A site that wants
non-refundable bookings needs only to display the words "free cancellation" to
obtain unattended commits from us. Possession of a string the adversary wrote
is not possession of a capability.

That sentence is struck. The handle remains **necessary and never sufficient**.

### The second kill: the invariant would re-open the one-corrupt-row scar

The design put its central law in `assert_valid` (`workflow.py:242-266`). That
function runs via `from_dict` → `from_params`, **unguarded** at
`worker.py:1171` and `anticipy_core.py:3572`, and inside a bare
`except Exception: return None` on the Send path. A stored SUCCEEDED row that
lost its `undo:` evidence entry would become permanently unparseable — and
`workflow.py:50-62` is a twelve-line scar block about exactly that: one
malformed row threw out of `hear()`, the event was marked error and never
retried, *"and nothing was ever said to him about any of it."*

**Rule that survives this card:** `assert_valid` must never grow a rule that
can be false for a legitimately stored row. If such a law is needed it belongs
in `succeed()` as a TRANSITION guard, mirrored in `workflow_guard.pb.js` and
`workflow_state.js`, or it uses the cautious-coercion shape of
`_state_after_unreadable` — never a raise.

### What a future Stage 2 would have to be

Not "captured handle" but **proven host**: a per-HOST allowlist where a host is
admitted only after a Stage 1 undo has run end-to-end on it, live, with the
site's own cancellation email in the owner's inbox and the receipt committed to
a repo file. The release becomes a fact **the system owns** rather than one
read off the site being acted upon. The `undo:` invariant would key on the
**post-receipt** capture only, never the pre-press one.

That is a different card, it depends on Stage 1 having produced real receipts
from real hosts, and it is not scheduled. Record any re-proposal and its
outcome in `docs/UNDO-LANE.md` the day it is made (Law 4).

### Consequence for the board

Moment #25 ("reversible things don't wait for permission") does **not** ship
from this card. Moment #28 (undo, with proof) does. That is a smaller claim
than the card's title and it is the honest one — and Stage 1 was the part both
judges could not break.
