Tables lose their column structure in this decoding — a row's cells arrive

ANTICIPY ENGINEERING PROPOSAL, V1
Two Hands: the Overwatch layer and the API hand
Anticipy acts through a browser today. This adds a second hand that calls
official APIs whenever one exists for the step at hand, and an Overwatch
layer that watches every task, learns which hand wins, and never needs a
hardcoded rule per app.
The short version
The pendant hears a commitment and the brain turns it into a task. Right now every
task goes to one place: the Chrome extension on the user's Mac, which clicks
through websites like a person would. That works anywhere, but it is slow, it costs
LLM steps, it breaks when a site changes, and it needs the laptop open.
Most of what people ask for touches apps that also have an official API: Gmail,
Google Calendar, Notion, Slack, Linear, HubSpot, Shopify, Stripe, Sheets. An API call
finishes in under a second, costs a fraction of a cent, does the same thing every time,
and runs from our cloud while the laptop is closed. We should use it every time it is
available. The problem is knowing when it is available, for this user, for this step,
without writing a rule per app.
That is what Overwatch does. Every task step gets a hand-agnostic description
called a capability signature. The router searches a live tool catalog for a matching
API tool, checks whether the user has connected that app, checks what the ledger
says about past success, and picks a hand. The browser hand stays the default until
the API hand proves itself on that exact kind of step. The Observer watches browser
runs, notices which app the agent was clicking in, and asks the user to connect that
app once so next time it is an API call. No hardcoding: the catalog is data, the
connections are data, the routing weights are data.

Why a second hand
HAND 1, FRONT OF THE HAND
Browser: the Chrome extension in the user's own logged-in Chrome
Works on any site, including ones with no API: Uber, DoorDash, airlines, banks, school portals.
Auth is free. The user is already logged in, no consent screens.
Slow: minutes per task, one LLM step per click. Fragile when a page changes.
Needs Chrome open on the Mac. Closed laptop means nothing happens.
Stays the default and the fallback. Nothing here gets removed.
HAND 2, BACK OF THE HAND
API: official app APIs through a per-user integration platform
Sub-second, deterministic, same result every run. A "send email" call is one call.
Near zero marginal cost: about $0.0003 per call on Composio's paid tier.
Runs in our cloud. The pendant plus phone can complete tasks with the laptop shut.
Needs the user to connect each app once through OAuth. Only covers apps that publish an API.
Used whenever it exists, is connected, and has earned trust for that step.
The honest limit. None of the integration platforms expose consumer actions for
Uber, DoorDash, Lyft, Airbnb, airlines, or Canadian banks. We checked Composio,
Pipedream and Zapier catalogs today. Those stay on the browser hand until sites
publish WebMCP or UCP manifests (both in early preview from Google, see
Sources). The API hand is for the "work and life admin" layer, which is most of what
the pendant hears.
Who we use
Pick: Composio as the primary catalog and auth vault, MCP as the wire protocol we
code against, and a thin internal Provider interface so we can add or swap vendors
without touching the router. All numbers below were read from vendor pages on Sept
5, 2026.

One task, two possible hands. The router decides per step, not per task. The ledger is the
only thing that changes over time, and it changes from outcomes, not from code.
Hybrid tasks are normal. "Book the table and email Sam the confirmation" is a
browser step (OpenTable) followed by an API step (Gmail). Routing is per step.
The catalog adapter has three inputs. Composio search today, official vendor MCP
servers as we meet them, WebMCP and UCP manifests read by the extension when
sites start publishing them. All three answer the same question: "is there a structured
tool for this signature?"
The vote stays. Multi-agent voting still decides the plan. Overwatch decides how each
agreed step gets executed.
Capability signature
This is the one abstraction that makes no-hardcoding real. Every recipe step is
written in terms of what it does, never how. Hands are compilers from signature to
action. The planner emits it, the router searches with it, the ledger is keyed by a hash
of its stable fields.
{
 "app_hint": "gmail", // planner's guess, may be null. Not a routing key.
 "verb": "send", // read | create | update | send | delete | pay | book
 "object": "email",
 "inputs": { "to": "sam@x.com", "subject": "Dinner confirmed", "body": "..." },
 "expected_effect": "recipient sees one new email in inbox",
 "side_effect": "write", // read | write | irreversible
 "account_hint": "work", // work | personal | null, resolved from context
 "signature_hash": "sha1(verb+object+normalized input keys)"
}

app_hint is advisory. The router confirms the app from the catalog match and, for
browser runs, from the Observer's host. If they disagree, the trace wins and the planner
is told.
expected_effect is what the verifier checks, the same way for both hands. Parity
means both hands produce the same verified effect, not the same screenshots.
side_effect is set by the planner and then tightened by the tool's own metadata. MCP
tool annotations like readOnlyHint and destructiveHint exist but the spec says to
treat them as untrusted, so they can only make a step stricter, never looser.
Router policy
Five generic rules. There is no rule that names an app. Thresholds live in config and
are tuned from the ledger, not by hand per app.
1. Search first. Ask the catalog for tools matching the signature, scoped to the user's
connected apps first, then the whole catalog. Keep the top 5. If no candidate scores
above match_threshold (start at 0.75 after LLM rerank), route to browser and stop.
2. Connected? If the best candidate's app is not connected for this user: browser now,
and enqueue a connect nudge for that app. One nudge per app, re-ask after 14 days,
never during a task.
3. Read steps. Connected and side_effect = read: run per the ladder stage for this
(signature_hash, app). Shadow stage runs both hands and compares verified results.
Promoted stage runs API only. If the Mac is offline, API is allowed for reads at any stage
because reads cannot hurt.
4. Write steps. Connected and write or irreversible: API only at the "assisted" stage
or above, and only if the user opted in for writes on that app. Otherwise browser. Never
shadow a write.
5. Score, then fall back. Where both hands are eligible, pick the higher score_h =
LB95(success_h) - 0.15 * log2(1 + p50_latency_h / 5s) - cost_weight * cost_h.
LB95 is the Wilson lower bound so a hand with 2 lucky runs does not beat a hand with
40 steady ones. Any API failure (401, 429 after one retry, schema error, verifier
mismatch) falls back to browser inside the same task if the Mac is online, else queues
and tells the user.
Why the browser stays the default. The browser has a track record and the API
hand has none. The ledger starts every new signature at "browser only" and the API
hand has to earn each rung with verified outcomes. This is the same gate discipline
as the intent model: nothing promotes without passing.

happened?"

Safety, both hands
One policy layer, two hands. Side-effect class, confirmation rules, per-user daily
budgets and a scope allowlist are evaluated before either hand runs. The API hand is
faster at being wrong, so it gets no looser treatment.
Irreversible always confirms. Payments, deletions, sends to more than N recipients,
anything with irreversible. Both hands. Confirm shows the exact payload, not a
summary.
Premium tools off. Composio bills some tools at provider cost plus 5% (browser
automation at about $0.70 per run). Block the premium class by default so the API hand
cannot quietly cost more than the browser hand.
Scopes are the minimum. Request the narrowest OAuth scopes the matched tools
need, and add scopes on demand through a re-auth nudge rather than asking for
everything at connect time.
Multiple accounts. Work and personal Gmail both connected is normal. account_hint
comes from context (who was on the call, which calendar). If ambiguous, ask once and
remember.
Audit. Every execution logs hand, tool slug, payload hash, latency, cost, verifier result
and the router's stated reason. The reason is a sentence: "API, connected, rung 2,
LB95 0.94 over 27 runs."
