# Anticipy pendant recovery audit — 2026-07-21

## Bottom line

Do **not** flash the pendant yet.

The uploaded iOS build is a real, valid TestFlight artifact and the firmware file is a real nRF52840 UF2 image. However, the end-to-end pendant product is not wired. The app can discover and reconnect to a BLE peripheral, but no code connects received Opus frames to either transcriber, neither transcriber connects to the brain, and the phone-side brain is never instantiated. The browser confirmation path also loops instead of completing a send.

The deeper architectural problem is that `Anticipy-pendant` is a second miniature backend, brain, extension, and phone app built beside the real Anticipy system. The real system is `/Users/omarebrahim/Anticipy-0707`, whose browser engine and frozen authenticated `/v1` phone contract are much more mature. The right recovery is to salvage the pendant transport into that product, not finish the duplicate PocketBase architecture.

## What is not built or not proven

### 1. Firmware is not auditable or reproducible

The repo contains only:

- `firmware/anticipy.uf2`
- `firmware/anticipy.hex`
- `firmware/anticipy_dfu.zip`

There is no firmware source, west manifest, board overlay, Kconfig, build script, pinned Omi revision, or build receipt. No one can safely review or regenerate the binary from this repository. Firmware update work must stop until the exact source and toolchain are recovered or rebuilt reproducibly.

### 2. The pendant audio pipeline is disconnected

`PendantManager.onOpusFrame` is declared and called, but no other Swift source references it. `TranscriberClient`, `LocalTranscriber`, and `BrainClient` are never instantiated.

The practical runtime is therefore:

```text
BLE notify -> frame buffer -> callback with no listener -> discarded
```

There is no path to:

```text
audio -> transcript -> canonical engine -> check-in -> Chrome -> proof
```

The uploaded app can show a Bluetooth connection while doing nothing with the audio.

### 3. Local transcription cannot consume the received data

The pendant manager produces compressed Opus `Data`. `LocalTranscriber.append` requires a decoded `AVAudioPCMBuffer`. There is no Opus decoder or converter in the Xcode project. Apple's speech buffer request is a PCM-buffer interface.

The official Omi Swift implementation uses `swift-opus` to decode each Opus frame to PCM before creating `AVAudioPCMBuffer`. That layer is absent here.

### 4. The BLE framing contract is unresolved

The Swift app treats byte 2 as an intra-frame fragment counter and concatenates fragments until the next zero. The canonical Anticipy comms contract treats the same three-byte prefix as `uint16 sequence + flags`, one complete Opus frame per logical packet, and requires gap detection plus decoder reset.

Because firmware source is missing, we cannot prove which interpretation the binary implements. The app also does not use the first two sequence bytes, detect missing packets, request/measure MTU, reset a decoder, or report audio gaps honestly.

### 5. Cloud transcription and brain code are dead and unsafe architecturally

The cloud transcriber and OpenRouter brain are not wired and no key-entry/storage flow exists. Putting model provider secrets in an app or extension would also be the wrong production boundary. The canonical product says the phone is an interface and the backend is the brain.

The canonical target is:

```text
pendant -> phone capture bridge -> authenticated WSS/backend -> transcript
          -> canonical orchestrator/memory -> /v1 check-ins -> canonical extension
```

### 6. A physical iPhone cannot reach the default backend

The shipped default is `http://127.0.0.1:8090`. On an iPhone, that address means the iPhone itself, not this Mac. The build contains that exact URL. It also lacks the local-network usage description and local-network ATS declaration required for a deliberate LAN-development path.

Production must use an explicit authenticated HTTPS endpoint. A temporary LAN/tunnel URL is acceptable only for a controlled development build.

### 7. Pairing and data isolation are not production-safe

- The app-generated job payload omits `owner`.
- The app fetches all jobs without an owner filter.
- All PocketBase collection rules are empty/public for list, view, create, update, and delete.
- The extension includes legacy unowned work in an owner's claim filter.
- Claiming is query-then-patch, so concurrent poll/SSE wakes can race.

This is not a multi-user production system. The canonical app's Clerk bearer and `/v1` ownership boundary should replace it.

### 8. Confirmation does not complete the action

For Gmail/calendar templates, the extension opens a prefilled page and sets the job back to `awaiting_confirm`. The app's **Send it** button changes that job to `queued`. The extension then opens another prefilled page and returns it to `awaiting_confirm` again. It never performs the confirmed send.

For autonomous jobs, a `needs_user` result also becomes `awaiting_confirm`, but there is no continuation token or approved terminal phase. Requeueing restarts the run and can pause again.

The canonical engine already has the correct model: prepare, create one durable approval, resolve that exact paused goal idempotently, execute once, and attach proof.

### 9. The Chrome extension is not active and its production timing claim is wrong

The local backend has no registered agent. The unpacked source declares 5-second poll and 10-second heartbeat alarms. Packaged Chrome extensions do not honor alarm periods below 30 seconds, so those production timing claims cannot be used as a liveness contract. Realtime plus an honest last-seen state is required.

The manifest also grants `<all_urls>` and `debugger` globally and does not implement the per-site grants/allowlist described in the handoff.

### 10. The proof suite simulates the parts it claims to prove

- `proof/test_anticipy_live.py` directly changes the job to `done` and writes `draft sent to Sarah`; Chrome did not do that work in the test.
- `proof/test_pairing_live.py` plays both the extension and app using HTTP requests.
- `proof/test_backend.py` calls itself a pendant but posts a hard-coded transcript directly. Its cleanup deletes every event and pendant record in the backend.
- Other scripts reference `/home/ubuntu/...` and evidence directories from the old machine.
- The brain test passes a deterministic heuristic, not a live model.

These are useful component tests, but they are not pendant-to-phone-to-browser evidence.

## Why the session failed

The session optimized for visible artifacts: a UF2, a simulator screen, a TestFlight upload, PocketBase records, and passing scripts. It did not enforce a single architecture or require each handoff claim to be demonstrated at the physical boundary.

That produced two systems:

```text
Real Anticipy:
canonical engine + canonical extension + memory/SMS + authenticated /v1 + Expo app

Devon pendant branch:
binary-only firmware + isolated Swift demo + public PocketBase + second brain + second extension
```

The duplicate system looked end-to-end because tests directly wrote the state that the missing components were supposed to create.

## Recovery decision

Keep:

- the UF2/HEX/DFU artifacts as forensic inputs, not as trusted release firmware;
- the CoreBluetooth UUIDs, restoration/retrieval ideas, and fragment reassembly as a starting point;
- the valid TestFlight build as proof that signing and delivery work;
- the canonical Anticipy engine, extension, `/v1` adapter, and Expo app as the product.

Discard or archive as non-production:

- the PocketBase data plane;
- the phone-side OpenRouter brain;
- the duplicate extension and its job schema;
- the current confirmation state machine;
- every “live proof” claim that was produced by direct record patches.

## Finish sequence

### Gate 0 — freeze and identify

1. Preserve the current firmware hashes and TestFlight build as immutable evidence.
2. Recover the exact firmware source/revision/toolchain, or rebuild it in a clean tracked tree.
3. Pin one shared GATT/frame contract used by firmware, iOS, fixtures, and tests.
4. Use `/Users/omarebrahim/Anticipy-0707` as the single product base. Create a normal working branch; do not build new behavior on the detached checkout or in the duplicate Swift app.

### Gate 1 — prove the downstream pipeline without hardware

1. Add the canonical `CaptureSource` boundary described by CP-3.
2. Implement a fixture/file source first.
3. Stream fixture audio through the real authenticated backend transcription route.
4. Verify transcript -> canonical orchestrator -> `/v1` check-in -> approval -> canonical extension -> proof for one ship-bar scenario.
5. Keep all provider secrets on the backend.

This gate must pass before Bluetooth work. It isolates product plumbing from radio/codec problems.

### Gate 2 — add the pendant transport to the canonical app

1. Create an Expo development client; Expo Go cannot run background BLE.
2. Add the native BLE transport with iOS central background mode and state restoration.
3. Implement the pinned frame decoder, sequence-gap metrics, decoder reset, battery/status/control characteristics, and bounded backpressure.
4. Feed the transport into the same `CaptureSource` used by the proven mock path.
5. Do not put transcription or LLM keys in the app.

### Gate 3 — make firmware reproducible

1. Restore source, board overlay, Kconfig, west manifest, Opus configuration, and build commands.
2. Produce UF2/HEX/DFU from a clean build and compare the declared protocol to the app fixture byte-for-byte.
3. Add a version/build identifier characteristic or status value.
4. Record current draw, sample rate, codec parameters, MTU behavior, and the exact hardware revision.

Only after Gates 1–3 are green should a new firmware image be flashed.

### Gate 4 — physical proof

With the pendant and iPhone present:

1. Inspect the device identity and current bootloader/firmware state before writing anything.
2. Flash the reproducible build.
3. Pair once in the foreground and verify the exact GATT characteristics.
4. Confirm live Opus frame counts, sequence continuity, decoded PCM, transcript text, and canonical task creation.
5. Walk out of range and return; verify pending reconnect and an honestly reported gap.
6. Lock the phone for 30 minutes and confirm continuous transcript/gap accounting.
7. Terminate the app under controlled conditions and verify CoreBluetooth restoration/reconnect.
8. Run one real reversible Chrome scenario, then one approval-gated send with proof.

## Definition of done

The pendant work is done only when one recorded run demonstrates all of this without direct database edits:

```text
real pendant microphone
-> reproducible firmware
-> BLE frames with gap accounting
-> canonical phone capture bridge while locked
-> authenticated backend transcript
-> canonical memory/orchestrator
-> /v1 check-in
-> user approval
-> canonical extension in the user's Chrome
-> single execution
-> visible proof in the app
```

Until then, the honest status is: **useful artifacts and partial transport code exist; the pendant product is not end to end.**
