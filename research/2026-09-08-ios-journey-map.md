# iOS journey map — 2026-09-08

## Scope and evidence

Read-only inventory of the current `cloudflare-backend` working tree, prompted by the replacement 100 lived exemplars guide. This is a **source-wiring audit**, not evidence of a TestFlight install or a successful real-account journey. No production endpoints, owner records, credentials, or `.env` files were read. Line anchors below describe the pre-fix tree; later edits may move them.

The parent completed the mandatory pre-edit `sh app/ios/Tests/run_all.sh` with exit 0 on build 171. Those pure-Foundation/source-contract tests do not establish that screens render correctly on a phone, that speech survives device interruptions, that OAuth works, or that an external action completed. A signed build, install, controlled owner, deliberately granted permissions, and downstream receipts remain release gates.

All paths below are repository-relative. `App` abbreviates `app/ios/Anticipy/AnticipyApp.swift`; `Backend` abbreviates `app/ios/Anticipy/Backend/AnticipyBackend.swift`; `Views/` and other unqualified iOS folders are under `app/ios/Anticipy/`.

Entrypoints: `App:82–119` constructs first-run/auth/Home routes, `App:222–260` handles listen/connect deep links and invalidates owner-bound handoffs. `FirstRunRoute.swift:49–85,255–285` defines the page sequence actually rendered by `OnboardingView.swift:161–169,267–289`; connection audience can remove only the optional apps beat. `Views/ContentView.swift:1273–1343` constructs the dashboard and actual Settings destination. `SettingsHomeView.swift:60–131` constructs the Settings destinations.

`SettingsView`, `SettingsAccessView`, `AskCard`, `HandlingCard`, and `FoundCard` are defined but had no production construction callsite at inspection time. Some helpers inside them are used; their existence is not evidence their complete UI is reachable. ## High-impact findings and implementation scope

1. **SOURCE-PROVEN, actual Home controls missing:** `.working` and `.question` render display-only views; `HandlingCard` / `AskCard` are uncalled. Wire the existing authoritative cards into actual thread and capture-detail paths, preserving fresh read/reconciliation and current owner's job/event identity. No second task-answer logic.
2. **SOURCE-PROVEN, declined source cannot recover:** actual source Settings has no reopen control; only dead legacy SettingsView calls `ContextGrants.reopen`. Add a clear action which only re-enables future asking; it must not grant OS/source permission or read facts immediately.
3. **SOURCE-PROVEN unsafe asynchronous ownership use; deterministic race reproduction needed:** `heard` awaits backend POST, then writes parent ID or buffers `account: accountID` using mutable current session state (`App:1089–1118`). A failed old-owner request completing after a new sign-in can label old speech as the new account. Unlike `writeAppReply:3291`, it has no captured owner/token completion guard. Capture authority before suspension; preserve the original owner stamp and never mutate a replacement owner's session. Test success and failure after sign-out, account switch and same-owner token replacement.
4. **SOURCE-PROVEN, supervised forget is not durable:** `read_veto` errors are swallowed after local UI removes the fact. A visible failed/pending state + owner-bound durable retry/readback is needed before claiming every fact is actually forgettable. Out of this bounded patch unless separately authorized.
5. **SOURCE-PROVEN limits, not successful live tests:** pendant audio is muted; notifications require app execution and permission; browser/mac setup URLs only hand off; owner memory has no full inspect/edit surface; first live speech/typed POST is not durably staged before request. Installed-device/background/OAuth/vendor-effect behavior is unproven.

The root authorized bounded fixes for findings 1–3 after the baseline passed. Version/project files remain root-owned. This document records the pre-fix map; append verification below rather than silently converting source analysis into a shipped claim.

## Controlled installed-build verification still required

Use one team-authorized disposable owner and deliberately permissioned devices/services. No production owner data or mutation without that authority.

- First-run every skip/deny/offline branch; sign out and sign in as a second disposable owner with requests in flight.
- Real phone speech and typed input → owned event → model decision → correct lane → visible result; interruption by lock screen, phone call/media, network loss and process restart.
- Actual Home queued/running Stop and standalone-question answer, including lost-response Check outcome; no blind repeated external action.
- Decline source → real Settings reopen → new contextually justified model offer → explicit OS permission → observed facts; revoke and confirm no further reads.
- Chrome pair/no-match/offline/stale-version/unpair, then one harmless controlled browser read and one explicitly approved disposable write with visible independent receipt.
- Calendar create/change/cancel with unique disposable record, local permission denial, stale approval, failure before/after save and exact EventKit readback.
- Add connected app → disclose → cancel or finish OAuth → canonical list; writes off/on/refused, revoked grant and failed vendor read.
- Supervised read → Stop/leave screen → no continued read after lease, fact veto with success/offline recovery before asserting forgetting.
- Delivered approval/answer alert on locked and suspended phone; distinguish local notification permission from SMS delivery and quiet policies.
- Read verified result/uncertain result/cancellation receipt, safe fresh retry, expand/copy/accessibility/dynamic type/reduce motion, no secret/internal error leakage.

Never use the 100 exemplars as literal prompt classifiers or canned output. Evidence should follow the user's actual path and the real state transitions, with identifiers kept in a controlled evidence ledger rather than copied into public reports.
