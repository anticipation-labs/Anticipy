## 2. The hostile page, and what it proved

`extension/tests/hostile_checkout.html` — 17 controls, openable in Chrome, and
simultaneously the fixture that `test_takeover_list.mjs` parses. One artifact, so
the manual proof and the automated one cannot drift. Every row is a disguise a
real site ships, not an exotic construction.

**Four got through on the first run.** Three shared one root cause:

> The extraction behind the stop opened with
> `if (!el || el.tagName !== "INPUT") return {}` — and `{}` is exactly what
> `protectedInput` reads as "an ordinary field, go ahead."

- **A card-expiry `<select>`** (row 4) — which is how essentially every checkout
  in the world renders card expiry. The select door asked about it, was told
  nothing, and wrote to it.
- **A `<textarea>`** (row 5) and **a contenteditable `<div>`** (row 6) — the
  latter is already indexed by `page_map.js` whenever it carries a `tabindex`,
  and writes already resolve to it through the active editable.
- The same `{}` handed `unquotedCode` an `undefined` `attrs` on the select door,
  so **a one-time code offered as a menu option was unguarded too** — the exact
  bypass that door was given `unquotedCode` to close, reopened one layer down.

The fourth is independent:

- **A "show password" toggle** (row 2) — `type="text"`,
  `autocomplete="current-password"`. Every such toggle flips the type attribute
  and leaves the declaration alone. `page_map.js:9` has always called that
  sensitive and printed `(sensitive field — never fill)` into the model's page
  map. **The map said never fill and the door filled it**, and only one of those
  two is a stop.
- And `autocomplete` is a **token list** — the spec's own example is
  `"section-blue shipping cc-number"` — while the check read the whole string
  with `startsWith("cc-")`. A card number declared exactly the way the spec says
  to declare it walked through.

Both write doors are proven through the **real step loop** with
`authorized: true` and a scope that plainly approves the errand, because a guard
that only holds when nobody authorised anything is not a guard.

### The row I did not fix, on purpose

Row 12 is a card field whose only signal is Spanish wording — no `type`, no
`autocomplete`. Catching it means a word list in N languages deciding what a
field MEANS, which is HARNESS-LAW 1 and would have been violation #25. The
honest instrument is the declared kind and that row declares none. The suite
**reports** it every run and pins it in neither direction: pinning it red would
block the only honest fix, pinning it green would forbid one.

## 3. What I built

**`readDeclaredKind` (`agent_loop.js:2984`)** — the page-side extraction, now
covering `INPUT`, `SELECT`, `TEXTAREA` and contenteditable, and resolving
`aria-labelledby` to the elements it names, which is where a component library
puts a CVV's accessible name. It reads declarations only. It is **exported so
the suite drives this exact function** rather than a copy — a copy is how a
guard passes its own tests and lets the field through. It reads no value, so
`page_map`'s redaction is not undone on the way to the guard.

**`protectedInput` (`:2814`)** — tokenises `autocomplete`; refuses
`current-password`/`new-password` regardless of declared `type`. `one-time-code`
is deliberately **not** added: `unquotedCode` owns it and must, because a code
the owner actually gave may be typed and a flat refusal here would re-break the
inbox side trip `40b3851d` built.

**Milestone photography (`:4143`, three call sites)** — the last frame before
something irreversible (after every gate passes, so a run stopped by a gate never
leaves a photo suggesting it was not), and the page as it stood when a done claim
was **verified**, not when it was claimed. Both `done` exits, because a second
exit is where the one that was updated is not.

**The deposit (`background.js:1246`)** — one row per errand to the evidence host,
multipart, agent credential, `owner_ref` compared server-side against the
credential's owner. The row id is named **first** in the receipt, because
`workflow_state` keeps the first 12 entries and that pointer is the only one
nothing else in the product can reconstruct. A failed deposit costs the errand
nothing and says so: the owner's table is booked either way.

**One row per errand, not one per milestone**, and this is a deliberate
disagreement with the card. The host keeps 60 rows across every errand this
product will ever run, on a 5GB volume that has been to 4MB free once. A second
row would also be **indistinguishable** from the first — the collection has no
column saying which milestone a picture is of. Every milestone is still recorded,
as a `shot:<milestone>@<url>` mark carrying no bytes, and a milestone whose
capture came back blank records `shot:verified-done(none)@…`, because "there is
no photo of this" is itself worth reading off a receipt six weeks later.

**The verdict that was being returned by two regexes** — see §5.

## 5. The Law 1 finding the coordinator sent, and the answer to "does it appear three times"

`verifyDone` runs five guards in front of the model audit. **Four of them are
fail-CLOSED**: `completionShapeGap`, `completionContradiction`,
`completionEvidenceGap` and `officialRecordEvidenceGap` each return a reason
string that is used only to reject, and none contains `verified: true` anywhere
in its body. They can say no. They cannot say yes.

**One thing could say yes.** `terminalReceiptEvidence` (`:1736`) is two regexes
over live page prose; when both matched with `effectState` set, `verifyDone`
returned `{verified:true}` and **returned** — the model never saw the page.

The break, reproduced verbatim in `test_done_is_not_a_word_match.mjs`: the
success alternation carries `booked|scheduled|registered` **and**
`cancelled|canceled` in one list, and nothing compared the matched verb to the
goal. Goal: *"book the appointment."* Page: *"Successfully cancelled.
Confirmation number: ABC-10023."* The approved facts — the patient, the date, the
time — all appear on a cancellation receipt for that same appointment, so the one
guard that could have caught it had no reason to fire. **Verdict: booked.**

**So the pattern appears ONCE, not three times**, and that is what makes this a
contained fix rather than a redesign.

Deleting `cancelled` closes the instance and leaves the class — `renewed` against
"cancel my subscription", `updated` against "delete the listing". That is
measured, not asserted: mutation MB below leaves the booking case green and the
renewal case red. So the observation is **demoted, not deleted**: it rides into
the auditor's prompt labelled as a shape and told in the same breath what it does
not establish, and the model returns the verdict.

**The tell that this was fail-open:** before the fix, the *genuine* booking
receipt passed for exactly the same reason the cancellation did — the shortcut
said yes to anything receipt-shaped. A guard whose true positives and false
positives have the same cause is not a guard.

Cost: one model call on errands that used to skip it, in a function that runs a
handful of times per run. A shortcut that can only ever say "yes" was buying
latency by skipping the only check that could catch anything.

`test_verification_fail_closed` had pinned the changed line **by its exact
punctuation** and went red on a reflow. Per second-door-criticals C2 the repair
is not to update the string: it now asks every `done` exit whether it names the
verdict that justified it, so a new exit that forgets is caught and a rewrap is
not.

### Two mutations the suite could not see, which is the finding

**M2 registered as ZERO on the first attempt.** Row 3 has a visible "Card
number" label, so the wording backstop caught it even with the token split
broken. A mutation a suite cannot see is a suite that would not have caught the
bug. The page was hardened: rows 16 and 17 declare their kind and say **nothing**
in words, so only reading `autocomplete` as the token list it is can catch them.
M2 then registered.

**M8 registered as ZERO.** The line that dropped the frame from the run's result
was `delete out.evidenceShot` inline at the call site; removing it leaked a 100KB
data URL into `params` on a hand-back and into the trace writer, and the suite
called it a pass — a screenshot of a logged-in page in a text column forever,
which is the exact thing the evidence host was built to avoid. A line no test can
see is a line that is not really there, so it became
`takeEvidenceShot` (`background.js:1231`) with a name and five checks, including
one proving the removal is **not** conditional on success — a `needs_user`
hand-back is precisely where `out` gets serialized. M8 now turns 3 red, and
making the removal success-only turns 1 red.

## 7. What waits on a deploy (Law 3 — repo-green is not done)

**Nothing in §3 is proven until a photograph reaches a phone.** `is_it_live.py`
reports production serving **0.8.4** against source **0.11.0**, and the committed
zip is missing `private_places.js` — so the live extension is not running the
second door at all, let alone this. Checked myself, and it is worse than the
brief said: see item 1.

What this work specifically needs, in order:

1. **A rebuilt zip, and the version number cannot be used to check it.** I opened
   `backend/pb_public/anticipy-extension.zip`: its `manifest.json` says
   **0.11.0**, matching source exactly — and the `agent_loop.js` inside it does
   not contain the `private_places.js` import at all. The bundle predates the
   second door and is stamped with today's version. **A byte-or-behaviour check
   that compares versions would pass while prod serves code without that door**,
   which is precisely the Law 3 failure mode, wearing a green light.
2. **`build-zip.sh` is NOT the problem** — the brief said the packager omits
   `private_places.js`; I ran its derivation over the current tree and the file
   **is** reached, through `agent_loop.js:18`. The packager walks imports and
   `chrome.scripting` injections and picks it up. The committed artifact is
   simply older than the import. The fix is a rebuild, not a packager change —
   and re-running `build-zip.sh` is enough to carry everything in this report,
   because all of it lives in `agent_loop.js` and `background.js`, both already
   packaged.
3. **That a PocketBase `file` field lands on `/pb_data/storage`.** Untestable
   here: there is no PocketBase binary in this tree. `start.sh` already prints
   `du -sk /pb_data/*` at every boot; watch it after the first upload.
4. **That `e.requestInfo().body` is populated for multipart**, which the guard
   branch binding `owner_ref` reads. It fails **closed** if not — the comparison
   fails and the upload is refused — which is the right direction to be wrong in.
   It would show as the extension unable to deposit at all.
5. **The takeover list against a real checkout.** The hostile page is faithful to
   the HTML, but Stripe Elements and its peers put the card field in a
   cross-origin iframe, which is a different code path (`inFrame`, index ≥ 1000).
   The offline suite cannot reach it.

## 8. CHEAP: what I did not build, and why

The card asks for a small model on navigation steps and a strong one at decision
points. It is not built — one `model` serves every step. I did not build it, and
the reason is the fix order in HARNESS-LAW 5, read backwards: a model tier is
step 4, and the thing that actually makes an errand cheap here is step 5's
structure, which **already exists**. Run 3+ of a known task shape replays the
route with **no model call at all** for every replayed step, and abandonment is
total and cheap on any checkpoint failure. Splitting the tier would save money on
exactly the runs that already cost the least, and would put a weaker model on the
navigation steps of run 1 — the run that has never seen the site, is reasoning
live, and is the one that mints the recipe every later run depends on. A bad
recipe compiled by a cheaper model is not a saving.

The honest cost pass the card asks for — tokens per errand before and after
recipes — is **not measured here**, because it cannot be measured offline: the
suites script the model and count calls, not tokens, and the meters that hold
real token counts (`agent_llm_meter`) are server-side and behind a deploy that is
three versions stale. Counting scripted calls and calling it a cost pass would be
a number with nothing behind it. It belongs with item 1 of §7.
