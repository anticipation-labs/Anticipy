# The actual iOS → Chrome customer journey

Date: 2026-09-08. Source inspection on `cloudflare-backend`, including the current uncommitted repairs. This report implements the replacement “Anticipy in real life” brief's evidence boundary: the person starts in the installed iOS app and the result returns there. A directly inserted event/job, simulated phone, mocked Chrome API, successful model answer, or green unit suite does not establish that journey.

This pass read source only. It did not read env files, tokens, browser profiles, customer records, or private audit artifacts; run a live gate; package an extension; change application source; or deploy. The paths below are source references, not instructions to execute their top-level code.

Worker claims it, builds context and asks the brain, which may remember, ask, act or stay quiet. | Actual microphone capture and permission state on the device, original text/speaker/capture envelope, processed event, and the next appropriate action. A developer-posted phone-shaped JSON body does not prove recognition or segmentation. |

The current direct-act patch refuses to narrate nonexistent work when no card was minted. | Persisted job ID bound to the source event(s), owner and approved scope; a brain `act` stamp alone is not a job. A deduped result may correctly refer to an existing card instead of creating a second one. |

Model requests go through paired `/agent/llm`; Chrome debugger/page-map actions operate the actual page. | Corresponding task trace, request status/provider metadata, observed pages and verified outcome. The actual destination's record is stronger evidence than a success-looking banner. |
| It asks for missing details or login | Browser returns `needs_user`, keeps hand-back/resume information on the job, and offers the page by badge/notification/popup. It focuses that page after an owner gesture. iOS renders the question from the job. | A clear task-specific question, accessible answer field, safe retained tab, no unauthorized submission. Login/password/2FA are completed by the account owner in Chrome, never invented or pasted into agent logs. |
| The person answers a task question | `confirm(job, ownerAnswer:)` uses `AnswerRoutePolicy`. Worker `handle_inbound` passes that context to the shared conversation path. | One accepted inbound event for the same pending answer, correct task resumed, remaining missing details still asked. | The person approves a ready plan | The explicit approval path builds version/scope-bound approval fields and PATCHes the job. A brief “yes” typed into conversation must be understood in context by the brain; the transport must not interpret the word. |

Worker `report_finished_jobs` also persists one app result under `job-result:<job ID>`; optional text delivery is separately fenced/recorded. | Finished card in the actual app, matching receipt and independent destination evidence. ## Recovery must be demonstrated, not narrated

- **Browser asleep / network interrupted:** recurring wake alarms are reasserted on boot/ping; active jobs renew leases. A hung cycle stops renewing its lease. Expired work without an uncertain effect can requeue, subject to a three-attempt ceiling. The real installed-MV3 test must run with popup, setup page and worker DevTools closed; keeping those open can conceal a missing wake alarm.
- **Login hand-back:** use the popup's Open the page, let the person sign in, then answer through the phone. A persisted tab ID is reusable only with its browser-session stamp. Restarting Chrome must not attach a reused numeric tab ID belonging to another page.
- **Effect may already have happened:** row writers persist the intent before the irreversible action. Stale recovery or failure calls `recoverUncertainEffect`; it reads the surviving intended tab and records a reconciliation verdict. The job parks instead of automatically resubmitting. Requeue requires a verified `not_applied` verdict for the same effect with evidence and owner words. A general “try again” is not a substitute.
- **Phone Stop / Don't do it:** the app writes canonical cancellation fields (`stopRunning` / `decline`), and the loop's liveness check prevents later actions. Existing external effects cannot be undone merely by changing status. If `effect_uncertain` was set, the phone warns that it may already have gone through. A true concurrency proof must compare destination records, not just the cancelled card.
- **Lost answer response:** `writeAppReply` reads the exact idempotency event; an unknown outcome offers reconciliation rather than blind resend. Repeat tap, connection loss and app restart must keep one event and the typed content recoverable.
- **Revoked browser:** owner unpair walks all pages before mutation, clears links and verifies no owned agents remain. The extension must stop claiming. Rejected private credentials have a three-explicit-refusal recovery path to a new pairing code. Generic network errors must not rotate identity. Re-pair through the UI; do not repair storage manually.
- **Old queued task:** Chrome parks work whose last queue update is over 12 hours old and asks whether it still stands, preserving the previous requirements. Human confirmation should not get stuck merely because the original creation date is old.

Two concrete limitations to preserve in the test plan:

1. The initial audit found the main Home composer cleared its draft before an unkeyed transcript POST. The current local patch stages transcripts atomically with stable external-event IDs before acknowledging the composer and uses exact owner/kind/ID readback after uncertain responses. Independent extracted-production Swift tests cover dropped response plus readback failure/restart and immediate double tap; they do not prove installed TestFlight behavior, iOS process termination, or actual device disk-failure recovery. Those customer actions remain release gates.
2. The browser queue patch excludes other hands' rows but the claim page is still capped at 10. Ten malformed yet filter-matching browser workflows can still hide an eleventh runnable row. Existing source tests establish the repaired cross-lane starvation, not universal queue liveness.

## Observe an existing customer-originated test-owner journey without injecting work

Prerequisite: the operator confirms the exact controlled account ID, the consenting tester, the time window and which diagnostic access is authorized. No searching across customers to find a convenient active agent. A new customer journey begins with signup in TestFlight, not an API-created `.invalid` fixture. A pre-existing fixture cannot be relabelled as a real onboarding run.

Use the account's normal authenticated read surface where possible. With narrowly authorized diagnostic service access, explicitly include that canonical owner in **every** query even though the credential could read more. Use bounded pages, narrow field selection and local redaction before sharing. Never include agent tokens, auth headers, phone numbers, email addresses, full transcripts, full model payloads or screenshots of unrelated content in a public report.

Read-only evidence collection can establish:

1. **Build/runtime identity:** public API health version/revision headers and the exact served ZIP bytes; an authorized GET `/admin/brain/status` for observed source hash, running child and current snapshot, filtering the report to the controlled owner. This status route reads the supervisor's stored observation; it does not start an owner. Missing/stale observation is unproven, not an instruction to wake or seed one.
2. **Pairing:** owner-scoped agents list selecting only ID, agent ID, `owner_ref`, paired, browser, last_seen/updated. No `agent_token`, no code enumeration and no `/agent/key` call just to collect a profile. The chosen agent must match the tester's visible extension; “newest paired globally” is invalid.
3. **Input:** owner-scoped events in the exact capture window. First collect metadata: ID, kind, source, device ID, created/capture stamps, decision, external-event ID. Confirm provenance with the tester's phone screen/timestamp; these fields alone do not cryptographically prove a device was used. Read only the necessary controlled test text if the decision needs interpretation.
4. **Task:** owner-scoped jobs; find the source-event ID(s) / lineage binding, not a fuzzy goal-text match. Record job ID, lane, workflow/version/state, created/updated, actor, attempts, lease expiry, effect uncertainty and receipt presence/binding. Treat the lease token itself as private. Read bounded trace/params only when required to distinguish mint, claim, model, permission or verification failure.
5. **Model hop:** `agent_llm_audit` records only explicit `[AUDIT:...]` prompt tags or an already-active `agent_audit_sessions` registration (`src/llm.ts:565–587`), not ordinary customer calls. Its absence does **not** prove that no model call occurred. Do not insert a tag/session merely to manufacture the missing evidence. If already-recorded audit data and D1 SELECT access are authorized, filter by this owner, agent/task and time; select status/model/timing and, when needed, individual usage fields extracted from JSON, never full prompts/provider payloads. Otherwise use the existing bounded job trace and human execution evidence, leaving provider accounting unproven. A successful proxy request is not a successful browser task.
6. **Return:** correlate job status/result/receipt with the idempotent app-result event and notification-status/outbox metadata. Then ask the tester to show the actual finished card. Do not call the delivery worker or resend an outbox item to make the observation look successful.
7. **Effect count:** where the operator has authorized read access to the controlled destination, read its actual sent item, draft, booking/event or transaction reference and count duplicates. Otherwise the human opens the destination. Do not submit a new task to fill a missing proof cell.

Diagnostic decision order: no original event → inspect the phone capture/post path; event unprocessed → inspect owner brain status; processed request without a matching job → inspect the brain's actual decision/mint outcome; job on another lane → inspect that hand; browser job queued → inspect pairing/version/poll/claim; running without progress → inspect lease/model/page boundary; terminal without receipt → unverified outcome; verified row without visible phone result → inspect app read/render/delivery. This ordering prevents “browser is alive” from being confused with “the brain gave it work.”

## Minimal deliberate release sequence

This is a plan, not a release performed by this report.

1. Finish source repairs and adversarial review; root runs the required pre-edit/final iOS suite, actual simulator compilation, Python/Worker/extension regressions. Preserve each known failed/unproven live hop instead of replacing it with a green local gate. Commit only reviewed named paths on `cloudflare-backend`; no main change.
2. If releasing the browser source changes, bump the four linked extension pins together: `extension/manifest.json`, `background.js:ENGINE_BUILD`, `AnticipyApp.swift:expectedExtensionVersion`, `StaleExtensionTests.swift`. Rebuild using `extension/build-zip.sh`, producing the three tracked ZIP aliases in `migration/workers/public`. Check every packaged module, alias digest and version pin. The API deploy script does **not** rebuild these automatically.
3. For iOS source changes, keep build/marketing values consistent in `project.yml` and the committed pbxproj (including embedded targets); do not guess the next available App Store Connect build. CI resolves collisions. Re-run the full required suite before the release commit.
4. Backend deployment is manual `brain-deploy.yml` with exact branch and `confirm=DEPLOY`. API mode runs two remote D1 fence migrations and the synthetic `live_api_release.py` automatically. Explicitly account for these production writes; they are separate release infrastructure proof, not the customer journey. Brain mode deploys the image and verifies source/process/snapshot. The actual command uses `--containers-rollout immediate` despite a nearby comment calling gradual the default; review fleet/cap/R2 preservation before dispatch. Do not improvise migration, seed or archive cleanup to satisfy the gate.
5. Signed iOS release uses `ios-testflight.yml` only. A qualifying push builds/tests; an explicit workflow dispatch or literal `[ship]` in the **commit subject** requests upload. The initial audit found the final `always()` summary could say “Shipped” after a failure. The current local workflow delegates to `release_summary.sh`, which distinguishes build-only, failed upload/processing, and uploaded-but-still-unverified outcomes; seven fixture tests independently pass. Its first real CI run is still unproven. Read the upload and Apple-processing steps and record actual upload build, processing verdict, commit and tester accessibility.
6. `asc-query.yml` with blank confirmation only reads who can install that build; invitation modes change tester/group state and require that specific intent. App Store Connect `VALID` does not prove TestFlight availability or installation. The human installs the intended build and records its on-device version.
7. Compare served API revision and **all** served ZIP bytes with the release. The human replaces/reloads the unpacked extension; verify the actual heartbeat now reports the intended version. Downloading a new ZIP alone changes no installed code.
8. Run the controlled person-driven journey below. Only after it passes can the release claim name the exact verified behavior. No blanket “perfect” claim follows from infrastructure green.

## Human/TestFlight + Chrome acceptance run

Use a fresh controlled account and a dedicated Chrome profile with only consenting test accounts. Record time, app build, extension version and backend release. Do not expose authentication secrets to the assistant. Start with read-only work, then one narrowly authorized reversible operation in the controlled destination. Real payments, third-party messages and bookings require their own explicit scope.

| Journey | Human action | Minimum pass evidence |
| --- | --- | --- |
| Cold start | Install intended TestFlight build, create account, complete actual permissions/onboarding, install served extension and enter its real code in iOS. | Both actual UIs agree, canonical owner matches, advancing current-version heartbeat; no fixture-created account or storage injection. |
| Typed browser request | Ask in Home for a fresh read/comparison using two controlled/public sources; vary task facts from the fictional guide. | One original typed event, matching browser job/claim, two actual page observations, verified result displayed in iOS with source links. No input sacrificed during refresh/navigation. |
| Spoken task | Speak a natural request with a correction or interruption, then wait normally. | Phone captures what was actually said; decision uses the corrected details; right task/lane appears; no duplicate or invented action. |
| Clarification | Omit a required fact, navigate away while drafting the answer, return, finish it, tap Send once, then test rapid repeat and a dropped response. | Draft survives; Send remains reachable with keyboard; exactly one accepted answer; only the right task resumes; unclear “yes” asks rather than broadly authorizing. |
| Login/permission | Request a controlled private page without being signed in; later sign in personally and answer from iOS. Separately revoke the relevant access. | Specific needs-user hand-back, safe Open the page gesture, no credential guessing, no unrelated account access; recovery or honest refusal after revocation. |
| Wake + interruption | Close extension popup/setup/DevTools while Chrome remains open; issue a fresh read from the phone. Later close/reopen Chrome during another controlled read. | Real background wake/claim, lease recovery and bounded attempt count; the user receives an ending or precise blocker, never indefinite silent handling. |
| Cancel | Start a controlled operation and tap Stop in iOS before its irreversible boundary. | Cancel persisted, no later external action, correct phone wording. Count destination records, not just UI status. |
| Ambiguous effect | In a safe controlled destination, interrupt after submission but before confirmation; inspect outcome before any retry. | No automatic second effect, preserved intent, reconciliation for the exact operation, duplicate count stays one or zero as actually observed. This cannot be certified from an injected row. |
| Result delivery | Return to Home/tasks after completion, background/foreground and inspect details. | Concise readable card, original result/receipt, accessible proof link; no duplicate app reply; optional text status describes the actual transport outcome. |
| Unpair/re-pair | Disconnect only this controlled browser from iOS, verify it no longer works, then pair through the displayed new/current code. | Old link cannot claim future work; UI and canonical state converge; another account's data never appears. |

Store each row as PASS / FAIL / UNPROVEN, with source-event/job IDs, redacted UI capture, timing and destination receipt where relevant. Existing customer-originated records can fill the observed server cells; absent live evidence remains UNPROVEN until the human performs that step. No new jobs or account resets are authorized merely to make the report complete.
